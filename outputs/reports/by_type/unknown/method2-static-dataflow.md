# 崩溃类型不明 · 方法二：静态数据流分析

## 覆盖情况

已复现 **34** 条，完成分析 **13** 条，其中 **9 条（69%）** 存在从参数到出错行的数据通路。

**69% 与「堆缓冲区越界」的 75% 处于同一水平。**

---

## 主要发现

### 一、通路存在率与堆越界类无差别

| 指标 | 本类型 | 堆缓冲区越界（对照） |
|---|---|---|
| 参数可达出错行 | **9/13 = 69%** | 59/79 = 75% |
| 出错行在循环体内 | 6/13 = **46%** | 36/79 = 46% |
| 函数带容量类参数 | 4/13 | 28/79 |
| 其中该参数从未参与比较 | **3/4 = 75%** | 13/28 = 46% |

**"出错行在循环体内"的比例完全相同（46%）**，
"容量参数未被比较"的比例甚至更高（75% vs 46%，但样本只有 4 条）。

### 二、修复方式也与堆越界类相同

方法三在本类型上统计到 12 条有效修复样本，其分布是：

| 官方补上的检查 | 条数 |
|---|---|
| 给「数据 / 容器长度」加上限 | **6** |
| 给「目标缓冲区容量」加上限 | **5** |
| 给函数新增长度参数 | 3 |
| 裁剪到合法范围 | 3 |
| 检查输入是否太短 | 2 |

**这与堆越界类的前三大修复方式完全一致**（长度上限、目标容量上限、裁剪）。

---

## 结论

从静态数据流的角度看，**本类型与堆缓冲区越界没有可区分的差异**：
同样的通路存在率、同样的循环内比例、同样的"缺上界检查"、同样的修复方式。

**这进一步支持"该类型应当被拆解并入堆越界类"的判断。**

---

## 本方法的局限

* 只覆盖 13/34 条。其余缺少出错点源码坐标，或定位不到漏洞版本源码。
* "容量参数从未比较"的 75% 建立在 **4 条**样本上，**不具统计意义**，只作方向参考。
* 与堆越界类的对比中，本类型样本量小（13 vs 79），比例差异可能来自抽样波动。
