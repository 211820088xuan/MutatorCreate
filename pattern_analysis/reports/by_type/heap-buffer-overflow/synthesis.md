# 堆缓冲区越界 · 综合报告

> 汇总三种互相独立的分析方法，给出该类型的统一结论与变异器设计依据。
> 样本：**111 条**已成功复现的真实崩溃（占全部 221 条的 50%，是样本量最大的类型）。
> 分报告：[方法一](method1-dynamic-taint.md) · [方法二](method2-static-dataflow.md) · [方法三](method3-fix-patch.md)

---

## 一、三种方法各自独立得到了什么

| 方法 | 分析条数 | 核心结论 | 比例 | 跨项目 |
|---|---|---|---|---|
| 一 · 动态污点追踪 | 41 | 越界量**由某个函数参数算出** | **68%** | 2 个项目 |
| 二 · 静态数据流 | 79 | **存在**从参数到出错行的数据通路 | **75%** | **9 个项目** |
| 三 · 修复补丁 | 69 | 官方补的是**长度/容量上界检查** | **前三类占 74%** | **6 个项目** |

三种方法的原理、数据来源、失效方式都不同：
方法一真的执行程序、方法二只读源码、方法三读的是**别人修好之后的代码**。

## 二、三种方法在哪些点上收敛

### 收敛点 1：出错的那个量来自函数参数

* 方法一（动态、具体执行）：**68%** 算出越界量来自某个参数
* 方法二（静态、只看通路）：**75%** 存在参数到出错行的通路

**两个比例接近，且是 18 条崩溃上同时成立**（动态与静态都确认）。
这是本项目第一次拿到"两种独立方法互相印证"的证据 —— 此前的结论都只有单一方法支持。

### 收敛点 2：这个参数缺少与容量的比较

* 方法二：有容量类参数的 28 条中，**13 条（46%）该参数从未参与任何比较**
* 方法三：修复新增行数中位 **7 行**、42% 不足 5 行 → **补的就是一个条件判断**；
  修复方式前三类（长度上限 24 · 裁剪 16 · 目标容量上限 11）全部是"给长度类量加上界"

**一个说"没有检查"，一个说"补的就是检查"** —— 两条独立证据指向同一处缺失。

### 收敛点 3（最强）：三个方法都独立地把这一类分成了两个亚型

这是本轮分析中**最有价值的发现**，因为三个方法的划分依据完全不同，却给出了一致的二分：

| | 亚型 A：逐元素越界 | 亚型 B：块操作长度失控 |
|---|---|---|
| 条数 | **96** | **13** |
| **方法一**（划分依据：一次访问的字节数） | 宽度 1/2/4/8 字节；归因到**第 1、4、6 个参数**（指针与下标） | 宽度 ≥1 KB，最大 2.7 亿字节；归因到**第 3 个参数**（＝`memcpy/memset` 的长度） |
| **方法二**（划分依据：容量参数是否被比较） | 容量参数 **36%** 从未比较；**41%** 在循环内 | 容量参数 **100%** 从未比较；**78%** 在循环内 |
| **方法三**（划分依据：官方怎么修） | **裁剪 16** 条（裁到剩余空间后继续） | 裁剪仅 2 条，改为**检查输入过短 4 · 校验魔数 1**（在解析头部时就拒绝） |

**三个方法的划分依据互相独立**（访问宽度 / 静态检查缺失率 / 修复方式），
**却指向同一个二分**，而且每一格都有机制解释：

* 亚型 A 是"循环里一轮一轮写、某一轮超了一点" → 所以幅度极小（74% 恰好压线）、
  所以裁剪是自然修法、所以下标/偏移是主因
* 亚型 B 是"长度字段被算成一个巨大值，一次性做块操作" → 所以完全没有上界检查、
  所以必须在输入解析阶段拒绝、所以长度参数（第 3 个）是主因

**旁证**：亚型 B 中有 4 条的越界长度**完全相同（201,851,904 字节）**，
其中两条位于 `ndlz4x4.c:544` 与 `ndlz8x8.c:462`，**由同一个提交一起修复** ——
说明这是同一个缺陷在兄弟文件里的两次出现，而不是四个独立巧合。

### 收敛点 4：校验点离崩溃点很远

* 方法二：数据通路长度中位 **36 步**（最长 817 步）
* 方法三：**48% 的修复不在出错的那个文件里**，45% 涉及多个文件

两个独立测量都说明：**参数要经过几十步传递才到出错行，因此检查通常加在上游。**

## 三、统一结论

```
      输入数据
         │
         ├─ 亚型 A（96 条）──────────────┐   ├─ 亚型 B（13 条）──────────────┐
         │                              │   │                              │
    某个参数携带「下标 / 偏移」      某个参数携带「块操作长度」
         │                              │   │                              │
    循环中逐轮累加，某一轮超出      长度由头部字段经公式算出，失控成巨值
         │                              │   │                              │
    该参数未与容量比较（36%）        该参数完全未与容量比较（100%）
         │                              │   │                              │
    越过边界 0～7 字节（74% 恰好压线）  一次性块操作写出上亿字节
         │                              │   │                              │
    官方修法：裁剪到剩余空间          官方修法：在解析头部时拒绝非法输入
         │                              │   │                              │
         └──────────────┬───────────────┘   └──────────────┬───────────────┘
                        │                                  │
              校验点通常在上游（48% 的修复不在出错文件）
```

**一句话概括**：一个携带长度或偏移的参数，在没有与缓冲区容量做比较的情况下，
直接决定了内存读写的位置或长度；官方的修复就是补上这个比较，
而且**通常补在上游的输入解析处，而不是崩溃点**。

## 四、对变异器设计的建议

### 建议 1：定位输入中的「长度 / 偏移 / 下标」字段，按语义角色而非函数名

**依据**：方法二显示参数名中 `src`(11) · `dest`(10) · `bsize`(5) · `srcsize`(5) · `src_offset`(5)
这组「源指针 + 目标指针 + 长度 + 偏移」的角色划分**跨项目复现**；
而函数签名 92.3% 只在单一项目出现、不可用。

**做法**：在输入格式中定位承担长度/偏移角色的字段（通常是头部里的 1/2/4/8 字节整数），
不要依赖任何项目专有的命名。

### 建议 2：取值集中在边界，而不是随机

**依据**：方法一实测 **74% 的越界恰好超出边界 0 字节**、**81% 的相对越界 ≤1%**、
九个项目的中位数全部为 0、最大也只有 115 字节。

**做法**：候选取值集中在 `容量−1`、`容量`、`容量+1`、`0`、`最大值`。
随机变异命中这种"精确压线"的概率极低 —— 这是本类型最重要的可操作结论。

### 建议 3：必须采用「先合法、后越界」的两阶段变异

**依据**：方法三显示修复动作以「拒绝」为主（30 : 18），且 **48% 的修复加在上游文件**；
方法二显示通路长度中位 36 步。

**做法**：第一阶段让输入通过所有早期校验（魔数、最小长度、字段自洽）；
第二阶段再让深层的长度/偏移超出实际容量。
**直接把长度改成一个离谱大数，很可能在早期就被拒绝、根本走不到崩溃点。**

### 建议 4：两个亚型使用两套算子

| | 亚型 A（96 条，主体） | 亚型 B（13 条，但机制清晰） |
|---|---|---|
| 变异对象 | 下标 / 偏移字段 | 头部的长度字段 |
| 变异幅度 | **小步长**，目标是刚好超出剩余空间 | **大幅改写**，目标是让公式算出远超容量的值 |
| 输入结构 | 需能被**多轮处理**（多块/多记录） | 需让长度字段的**编码形式**落入异常区间 |
| 附加算子 | —— | **截断到极短**（4 条修复是"输入过短"检查） |

**亚型 B 的一个可利用特点**：4 条崩溃得到完全相同的失控长度 201,851,904 字节，
说明该值由头部字段经**确定性公式**算出 → 反推该公式即可**定向构造**触发输入，
而不必依赖随机搜索。

### 建议 5：读越界与写越界的比例悬殊，但严重性相反

方法一实测 **读 82 : 写 27**。读越界数量多（信息泄露），写越界数量少但严重性高（可控制流）。
若目标是发现高危漏洞，应对**写越界**给予更高权重 —— 亚型 B 中写:读 = 7:6，
即**块长度失控更容易导致写越界**。

## 五、必须同时说明的限制

### 1. ⚠ 最强的那一批证据来自单一项目

| 交叉层级 | 条数 | 涉及项目 |
|---|---|---|
| 方法一 + 方法二同时成立 | 18 | c-blosc2 **17** · pcre2 **1** |
| 三种方法全部指向同一处 | 14 | **c-blosc2 14（仅 1 个项目）** |

本项目此前发生过一次同类误判：曾以为找到了「崩溃点函数签名的共性」，
后来发现 **92.3% 的签名只出现在单一项目里** —— 那不是漏洞共性，而是一个项目的代码风格。

**因此需要区分两类结论的可信度：**

| 结论 | 证据来源 | 可信度 |
|---|---|---|
| **越界幅度极小（74% 压线）** | 全部 111 条的崩溃报告，覆盖 **9 个项目** | **高** |
| **参数语义角色跨项目复现**（src/dest/长度/偏移） | 方法二，覆盖 **9 个项目** | **高** |
| **修复集中在长度/容量上界检查** | 方法三，覆盖 **6 个项目** | **高** |
| **48% 的修复在上游文件** | 方法三，覆盖 6 个项目 | **中高** |
| **两个亚型的划分** | 三个方法一致，但亚型 B 仅 13 条、有效补丁样本 8 条 | **中** |
| **参数位置的具体分布**（rdi/rdx/…） | 方法一，仅 **2 个项目** | **低，待补样本** |

### 2. 方法一的覆盖率是主要短板

只完成 **41/111** 条。未覆盖的 70 条集中在 libavc(22) · hdf5(21) · hunspell(13) 等项目，
原因是它们的分析用程序副本尚未构建成功。
**补齐后方法一的跨项目性才能与方法二、三对齐**，届时"参数位置分布"这条才能升级。

### 3. 反面情况

* 方法一有 **10 条**虽然执行到了出错点，但越界量**来自常量或局部变量**、与参数无关
  → 这部分对变异策略没有指导价值（约占有分析结果样本的三分之一）。
* 方法一有 **3 条**未能执行到出错点（崩溃报告里的源码行号与重新编译后的程序对不上）。
* 方法二的"46% 缺检查"是**下限**（检查若用中间变量或结构体字段则识别不到）。
* 方法三只覆盖能找到修复提交且真改源码的子集（69/111）。
* pcre2 的 JIT 相关崩溃**结构性不可分析**（出错行在 JIT 代码生成器内部，
  而分析副本必须关闭 JIT）。
