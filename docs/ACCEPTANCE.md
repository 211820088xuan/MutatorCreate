## 1. 主线任务

### 1.1 项目最终目标

**实现"错误型激发的模糊测试增强"**：让模糊测试工具更高效地触发（激发）软件中的错误（崩溃/漏洞）。

### 1.2 当前阶段任务

本阶段聚焦于 **Mutator（变异算子）的生成**。变异算子是模糊测试中"负责改写输入"的组件。默认的变异算子随机改字节，效果有限；我们要基于已知崩溃，生成一个"更会改"的变异算子。

### 1.3 方法框架

```
已知崩溃  →  分析崩溃信息  →  提取某种共性  →  应用到自定义 mutator  →  增强模糊测试
```

### 1.4 本阶段尝试的设计方向

```
分析 crash 轨迹  →  LLM 分析指令级的漏洞触发模式  →  转换成 mutator
```

> 即：把崩溃轨迹（崩溃时的调用栈、机器指令）交给大模型（LLM），让它总结"这一类漏洞在指令层面是怎么被触发的"，再据此写变异算子。

**结论预告**：这条设计方向**没有走通**。原因详见第 3 节，最终的变异算子改用另一条更有效的路线完成（第 4、5 节）。

## 2. 执行过程

### 2.1 数据准备：复现崩溃、提取指令信息

**复现崩溃**：从 OSS-Fuzz 复现了约 240 条真实崩溃，覆盖 16 个开源项目（c-blosc2、hdf5、libavc、hunspell 等）。

| 崩溃类型 | 数量（约） | 通俗解释 |
|---|---|---|
| 堆缓冲区越界 | 111+ | 读写越过了堆内存边界（最常见） |
| 崩溃类型不明 | 34 | 报告不规范，实际也是堆越界，已并入上一类 |
| 使用未初始化的值 | 14 | 读了从没赋值过的内存 |
| 释放后使用 | 13 | 内存已释放还去用 |
| 栈缓冲区越界 | 13 | 越过了栈上局部数组边界 |
| 全局区越界 | 11 | 越过了全局数组边界 |

**提取指令信息**：对每条崩溃，提取"崩溃那一刻的机器指令"相关信息——故障指令、寻址方式、读写方向、访问宽度、是否有下标缩放、崩溃前的一串内存访问、源码位置等。最终 **107 条崩溃拿到了真实有效的指令信息**，其中 91 条进入后续分析。

### 2.2 路线 A：LLM 分析指令级共性（原设计方向）

采用 DeepSeek（deepseek-v4-pro），分两步：

1. **逐条分析**：把 91 条崩溃的指令信息 + 源码片段逐条喂给 LLM，让它按固定格式回答（地址怎么算、下标来自哪、缺不缺边界检查、读还是写、宽度多大等）。结果 **91 条全部成功解析，0 失败**。
2. **跨条归纳**：把同一类崩溃的分析结果汇总，让 LLM 总结共性，并写成"可被程序自动检验的规则"。

**设计原则**：LLM 只负责"提假设"，结论由代码在原始数据上重新验证，不采信 LLM 自己报的数字。并预先定死过关门槛（命中率 ≥ 60%、至少跨 2 个项目、最大单项目占比 ≤ 70%、留出验证防过拟合）。

### 2.3 路线 A 的对照组检验（发现问题）

LLM 共提出 17 条共性结论，2 条通过门槛：

1. "85% 的堆越界，寻址方式是'基址+偏移'或'寄存器间接'"
2. "82% 的未初始化崩溃，故障指令涉及内存操作数"

这 17 条结论有个隐患：它只回答"在本类崩溃里占多少"，没回答"在别的崩溃里是不是也这么多"。于是补做**对照组检验**——把同一条规则拿到其它类型崩溃上再数一遍，算"区分度"：

| 结论 | 堆越界里 | 其它崩溃里 | 区分度 | 判断 |
|---|---|---|---|---|
| "地址是基址+偏移" | 85% | 82.5% | +0.026 | **没有区分度** |
| "涉及内存操作数" | 82% | 65% | +0.172 | 只有一点点 |

**结论：LLM 总结出的指令级共性没有区分度，不能作为设计变异算子的依据。** 原设计方向在此被证伪。

### 2.4 路线 B：经典统计得出的 4 条硬结论（真正有效）

用三种互相独立的方法（动态污点追踪、静态数据流分析、补丁分析）对崩溃做了统计，得出 4 条证据强、能直接用的结论：

1. **越界通常"刚好压线"**：74% 的堆越界超出边界 0 字节，9 个项目的中位数全是 0。→ 变异要改到"容量 ±1、0、极大值"这类边界值。
2. **要"先合法、后越界"**：48% 的官方修复在上游解析处，数据从入参到崩溃点平均经过 36 步。→ 先让输入合法通过检查，再到深处越界。
3. **认字段要看"角色"不看名字**：函数签名 92.3% 只在单一项目出现，但"长度、偏移"这类语义角色在 9 个项目里反复出现。→ 找"长度/偏移"字段，而非某个函数名。
4. **堆越界分两种亚型**：亚型 A（96 条，循环里逐个小步越界）和亚型 B（13 条，长度字段被算成巨大值、一次性大块越界），要分别用不同策略。

### 2.5 变异算子的设计与实现

基于 4 条结论，选崩溃最多、构建最快的 **c-blosc2**（压缩库）作为第一个目标。

c-blosc2 解压入口要求头部声明的"压缩后大小"（cbytes）必须等于输入真实长度，否则直接拒绝。头部三个长度字段位置固定（16 字节头）：

| 字段 | 字节位置 | 含义 |
|---|---|---|
| nbytes | 4–7 | 解压后大小 |
| blocksize | 8–11 | 块大小 |
| cbytes | 12–15 | 压缩后大小（= 整个输入长度） |

**算子设计**（`blosc2_mutator.c`）核心三件事：

1. **保住"合法外壳"**：每次变异都同步改好 cbytes，维持 `cbytes == 文件长度`，让变异进入解压逻辑（默认变异器会频繁破坏这一点、被入口拒绝）。
2. **专改长度字段到边界值**：把 nbytes / blocksize 改成"容量 ±1、0、极大值"等刁钻值。
3. **数据部分交给默认变异器**：压缩数据本身交给默认变异器探索。

策略权重：改 nbytes（28）、改数据并同步 cbytes（34）、改 blocksize（14）、改头部其它字节（8）。

### 2.6 效果验证

在 c-blosc2 漏洞版本（提交号 `4e231e35`）上重新编译，产出"默认"和"带算子"两个版本，同一批种子、同样时间、多轮对比：

| 配置 | 覆盖率（15 轮中位数） | 速度（次/秒） |
|---|---|---|
| 默认变异器 | 93 | 28380 |
| 本算子 | **1222** | 23866 |

**覆盖率是默认的约 13 倍，速度只慢 16%。** 本算子结果稳定（1062–1316），默认忽高忽低（68–627，靠运气）。

验证中还确认：算子挂载成功、自身 20 万次运行无崩溃、对 13 条真实 c-blosc2 崩溃输入的格式解析 100% 正确。

## 3. 关键发现：原设计方向为什么行不通

这是本阶段最重要的分析结论，直接关系到后续方向。原方向失败，是**三个问题叠加**的结果：

### 问题一：指令层面描述的是"症状"，不是"原因"

- 指令信息能精确描述"崩溃瞬间发生了什么"（读还是写、写几字节、地址怎么算）——这是**症状**。
- 但变异算子要改的是**输入**，它需要知道"改输入的哪个字节、改成什么，能触发崩溃"——这是**原因**。
- **症状 ≠ 原因**。中间缺一环"输入字节 ↔ 越界参数"的映射（缺口 B）。

### 问题二："找共性"这个任务本身就问错了问题

- 我们让 LLM"在这类崩溃里找共同点"，它返回的是"出现率"（85% 的崩溃都这样），而不是"区分度"（这类崩溃**比别的崩溃更**这样）。
- 因为没给 LLM 对照物，它分不清"这类特有的特征"和"所有崩溃的共同长相"。
- 对照组检验证实：85% 的堆越界是"基址+偏移"寻址，但 82.5% 的其它崩溃也是——没有区分度。

### 问题三：内存安全类漏洞在指令层本来就难区分

- 堆越界、未初始化、释放后使用，在指令层**都表现为"一次内存访问"**，互相分不清。
- 真正能区分的信号（哪个长度字段、缺不缺边界检查）在**源码/输入层**，不在指令层。

### 一句话总结

> **原方向把分析放在了"症状层"（指令级），又问了"找共性"这个错问题，所以 LLM 给不出"有区分度、可操作"的结论。这不是 LLM 能力问题，而是分析层面和提问方式的问题。**

---

## 4. 实际有效的结论

真正有效的是第 2.4 节的 4 条统计结论（边界值、两阶段、语义角色、亚型二分），它们全部来自**源码/输入层**的分析，而不是指令层。

此外，还打通了"输入字节 ↔ 越界参数"的映射：用"敏感性扫描"（逐字节改、看越界宽度是否变化）成功定位了长度字段，例如 ndlz 系列崩溃的长度字段在 byte 41–48，OSV-2021-639 的在 byte 103–106。

## 7. 已知局限与未完成事项

1. **变异算子只针对 c-blosc2 一个项目**，尚未跨项目通用。"长度字段在哪个字节"每个格式都不一样，通用化需要"自动定位"能力，这是未完成的难点。
2. **尚未证明"覆盖率提升能转化为更快找到崩溃"**：90 秒内默认和自定义都没能重新触发那条最难的历史崩溃，需要更接近崩溃的种子或更长时间验证。
3. **通用化的"字段地图"设计仍在方案层**，且经调研它只适合二进制结构化格式（约 44% 的崩溃），文本格式需要另一套思路。

---

## 8. 后续方向建议

详见本文档附带的"方向反思"。要点是：**把分析层面从"指令级"下移到"源码/输入级"，把问题从"找共性"改成"找可操作的触发条件"，并用现成的结构感知工具补上"自动定位字段"这一环。**
