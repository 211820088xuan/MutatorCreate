## 步骤 1 · F4 的「同名 / 别名 / 经字段」分布

### 做法

对 60 条 F4（裸指针）样本，取两处**pin 源码**：

| 一侧 | 来源 |
|---|---|
| 释放 | `facts.sites[kind=free].file:line` → 按 pin 用 raw HTTP 取**那一行**（复用 R12 的 `backfill_free_code.fetch`） |
| 使用 | `facts.crash.site.file:line` → 同样取那一行 |

**两个文件分开取**（限制 24）—— 实测确实不同（`tree.c` vs `xinclude.c`）。

**⚠️ 一开始我用了 `facts.crash.code`，那是错的**：它是**候选子表达式的 `|` 分隔集合**，
不是一行源码。改成读 pin 源码后，`ARVO-372547409` 才从"别名"变成正确的"同名"。

### 为什么这 4 条会误判成"同名"

**只用根标识符相同来判，会漏掉两种情况**：
1. **名字复用**（不同函数里的同名变量，值经字段/参数传来）—— `ARVO-42486565` / `ARVO-42497161`；
2. **顺序相反**（`use` 在 `free` 之前）—— `ARVO-42488049` / `ARVO-42488833`，它们根本**不该**连上。

**这两类都不是"判据没调好"，是根标识符这个信号本身不够。**

### 顺带发现的 `facts` 数据质量问题

| 现象 | 例子 |
|---|---|
| `free_line` 指向的**不是 free 语句** | `ARVO-42479359` 的"释放行"是一个 `}` |
| `free_code` 为空但 `free_file` 有值 → 取不到源码行 | `ARVO-42488049`、`ARVO-42488833`、`ARVO-42494732`（`src/in_dxf.c` 的 fetch 返回 None） |

**这就是为什么"自动化分类"只能当粗筛：`facts` 的释放点本身有噪声。**
