### 为什么这 4 条会误判成"同名"

**只用根标识符相同来判，会漏掉两种情况**：
1. **名字复用**（不同函数里的同名变量，值经字段/参数传来）—— `ARVO-42486565` / `ARVO-42497161`；
2. **顺序相反**（`use` 在 `free` 之前）—— `ARVO-42488049` / `ARVO-42488833`，它们根本**不该**连上。

**这两类都不是"判据没调好"，是根标识符这个信号本身不够。**

### 回归：✅ 通过

```
  point(free)=USABLE  point(use)=USABLE
  flows=67   paths=67   has_expected_path=True   175.8s
  @@FLOW  L12284:pair => L12267:pair => L12267:pair != NULL => L12267:pair != NULL && pair->code == 0 => ...
```

**⚠️ 回归判据要改**：R17 说"第一条路径必须是 `L12284:pair → L12267:pair → L12267:pair->code`"，
但**流的顺序不稳定** —— 同一份图、同一个查询，三次运行都是 `flows=67`，
**第一条路径分别是 `L12291`、`L12291`、`L12284`**。

**所以判据改成"是否存在一条 源 L12284 → 汇 L12267 的路径"**（`has_expected_path`）。
实测：`paths=67`，其中**包含**期望路径 ✅

**这是 R17 留下的一个隐患**：它把"第一条路径"当成硬判据，
但那取决于引擎的遍历顺序，**不是稳定性质**。

## 步骤 5 · 结论与 llm04 的可行性判定（收口）

### 5.1 能力 A 的真实覆盖面

| 形态 | 占 110 条（核实后） | 数据流能做？ | 为什么 |
|---|---:|---|:---:|
| **F4 同名** | **12.7%** | ✅ | 释放的裸指针在**同一个函数**里被读取 |
| F4 别名 | 37.3%（含在"释放根不在"的 41 条里） | ❌ | `reachableByFlows` 是**值流**，不做别名分析 |
| F1 经字段（结构体字段） | 5%（6/110） | ❌ | CPG 有 **10,180 条断掉的 `MEMBER` REF 边** |
| 名字复用 / 顺序相反 | 3.6%（4/60） | ❌ | 不是"同一实例的 UAF"，或本就不该连上 |
| F7 realloc / F3 容器 / F8 delete / F6 间接 / F9 判不出 | 其余 | ❌ | 形态本身不匹配 |

**一句话：llm04 探测器建起来之后，能覆盖 110 条真实 UAF 里的约 12.7%（14 条）。**

### 5.2 召回有统计意义吗

**没有。** 本轮的合格正例只有 **1 条**（`ARVO-42494732`），因为步骤 3（扩样本）被跳过。
**12.7% 是"形态分布"上的覆盖面，不是"召回"。** 两者别混。

### 5.3 llm04 值不值得建

按用户的阈值表：**12.7% 落在"10–30% → 边际，要看它能不能解锁至少一个新项目"**。

**但它解锁不了任何新项目**（5.4 的证据），所以**结论仍然是：不值得建** ——
**理由不是"覆盖面低"，而是"覆盖到的那一类，恰好没有一个候选项目有"。**

### 5.4 对 igraph / libxml2 / leptonica 的影响

| 项目 | 它的 UAF 属于哪一类 | llm04 建起来能落地吗 |
|---|---|---|
| **igraph** | `ARVO-42491546`：`t` 被 `igraph_Free(t)` → **别名** `v` 读到 `v->end` | ❌ **别名**，做不了 |

| **libxml2** | `ARVO-42486565`：**经结构体字段**（`ctxt->incTab[nr]->ref`） | ❌ 字段级断边 |
| | `ARVO-42533950`：`cur->ns->prefix` —— hmm，**这一类是"同名"** | ⚠️ **理论上能做**，但它的汇点文件 `list.c`/`tree.c` 覆盖率要单独查 |
| **leptonica** | `ARVO-42488049` / `ARVO-42488833`：`pix->refcount` —— **顺序相反**（B 类） | ❌ 不是同一实例的 UAF |

**→ 三个项目里没有一个的 UAF 能靠 llm04 落地。**
libxml2 的 `ARVO-42533950` 是唯一形态上"同名"的，但它在 R15 修守卫 1 之后**站点归 0**

### 一句话收口

**不是工具选错了，是这类 UAF 的形态本身就不适合静态数据流。**
R11 说"跨函数扫描器支持的形态在 110 条真实 UAF 里占 0"；
R19 说"换成 Joern 的跨过程数据流，也只能覆盖 12.7%"。
**两次都是同一个结论：这些 UAF 的"释放点"和"使用点"之间隔的不是数据流，是别名/字段/参数。**

+| 项目 | 它的 UAF 属于哪一类 | llm04 能落地吗 |

+### 与限制 7 串起来
+
+- **限制 7**（R11/R12）：跨函数扫描器支持的形态在 110 条真实 UAF 里**占 0**；
+- **限制 25**（R19）：换成 **Joern 的跨过程数据流**，也只能覆盖 **12.7%**。

+**两次都是同一个结论：这些 UAF 的"释放点"和"使用点"之间隔的不是数据流，是别名 / 字段 / 参数。
+不是工具选错了，是这类 UAF 的形态本身就不适合静态数据流。**

+## 限制 27 · 数据流的"第一条路径"不是稳定性质，回归判据要改成"是否存在"
+
+R19 回归实测：同一份图、同一个查询，**三次运行都是 `flows=67`，但第一条路径分别是

+
+**所以回归判据必须是"是否存在一条 源 X → 汇 Y 的路径"**（`has_expected_path`），
+**不能是"第一条路径等于 …"**。R17 报告里那条判据是错的。

### 下一步建议

**跨函数 UAF 这条线到此收口。** 如果将来还要碰它，唯一有价值的方向是：

| 优先级 | 做什么 | 为什么 |
|---|---|---|
| P1 | **别名分析**（`t` → `v`） | 占 F4 的 57%。很可能**超出 Joern 值流能力**，要另找方法（Steensgaard / 指向分析） |
| P2 | 修 **10,180 条断掉的 `MEMBER` REF 边** | 决定"经字段"那 25% 能不能做 |
| P3 | 去重那 110 条里的 `ARVO-*` / `OSV-*` 重复样本 | 形态统计才会准 |

**但在做这些之前，应该先问一个更根本的问题**：
既然 87% 的跨函数 UAF 都不是静态数据流能表达的，**这个类别的 mutator 到底该怎么生成**？
R9–R19 十一轮的经验是：**能落地的只有"同函数 + 裸指针"这一种**（libredwg，617 vs 0）。
