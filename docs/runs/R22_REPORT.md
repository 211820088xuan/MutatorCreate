# R22 报告

日期：2026-11-07
唯一问题：**"没有第二个落地项目"是真的没有，还是因为工具当时是坏的？**

> 出发点（不重复论证）：R21 查出 `s5_6_lib.blocks()` 两个 bug（假设 Allman 风格、`} else {` 判不出来）。
> `blocks()` 是 `flow()` / `step()` / `loop_back` 的基础 → **所有 K&R 风格项目的控制流分析之前全是错的**。
> 证据：修好后 leptonica 的 `loop_back` 站点从 **0 变成 6**。

### leptonica 的那 1 个站点：核实为假

```
  pixRankBinByStrip:3065→3064 (loop_back) var=array
```

**pin 源码**（`src/pix4.c`）：
```c
3059:        for (i = 0; i < nstrips; i++) {
3060:            pix2 = pixaGetPix(pixa, i, L_CLONE);
3061:            pixGetRankColorArray(pix2, nbins, type, 1, &array, NULL, 0);   ← 下一轮重新赋值 array
3062:            if (array) {
3063:                for (j = 0; j < nbins; j++)
3064:                    pixSetPixel(pixd, j, i, array[j]);                    ← 使用
3065:                LEPT_FREE(array);                                     ← 释放
3066:            }
3067:            pixDestroy(&pix2);
3068:        }
```

**释放（3065）→ 下一轮外层循环头（3061）重新赋值 `array` → 才使用（3064）** —— **不是 UAF**。

**这是 R21 记录的那一类"跨嵌套循环重赋值"**：回边是**内层** `for`（3063），
重新赋值在**外层** `for` 头（3061）—— 现有守卫的窄范围覆盖不到，**要路径敏感分析**（不做）。

**已在 R21 填进台账（`verified_in: R21`）。本轮复核结论一致。**

### gpac 那 1 个站点为什么消失了

`gf_free(ar)` 之后读 `ar->type`（R7 核过是真的）。重扫后消失，说明它被**新加的守卫**挡掉了
（`if/else` 互斥 或 `exit` 或 `use is same` 的判定变化）。
**gpac 靠 `--fault-anchor`，不是候选**，所以不影响本轮结论；但**这是一个需要单独查的回归** ——
**真实站点被守卫误杀了**。记进限制。
