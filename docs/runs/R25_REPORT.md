### 🔴 第一版核对层有 bug（已修）

第一版 `FREE_RX` 只认**以** `free`/`Free`/`FREE` **结尾**的名字：

```python
r"\b\w*(?:_free|Free|FREE|free)\s*\("       ← 只匹配结尾
```

结果 144 条被记 `no_free_call` 丢弃。**查它们的释放行到底是什么调用**：

| 调用名 | 条数 |
|---|---:|
| `dxf_free_pair` | **49** |
| `dwg_free_object_private` | 17 |
| `FREE_IF` | 9 |
| `dwg_free_object` | 8 |
| `dwg_free_eed` | 7 |
| `free_array_hdls` | 6 |
| `freea` | 5 |
| `dwg_free_xdata_resbuf` | 1 |
| …其余（`calloc` 11 / `memset` 2 / `strdup` 1 / `dwg_add_APPID` 2 …）**确实不是释放** | |

**→ ~102 / 144 是把项目自己的释放**包装函数**判死了。**

修法（这是修 bug，不是放宽）：`free|Free|FREE` 出现在名字**任意位置**都算：

```python
r"\b(free|kfree|cfree|delete|realloc)\s*\(|\b\w*(?:free|Free|FREE)\w*\s*\("
```

修完后核对通过率 **56.0% → 85.7%**。

### ⚠️ 但要看清楚：**两个端点都圈到了，是配对错了**

原始候选里有（都是 `b016` 批，`dxf_objects_read` 那个函数里）：

| 批次 | 候选 | 自报 confidence | 核对 |
|---|---|---|---|
| b016 r2 | `src/in_dxf.c:**12284** → 12287` | **high** | ✅ 通过 |
| b016 r2 | `src/in_dxf.c:12275 → **12267**` | low | ✅ 通过 |
| b016 r1+r2 | `src/in_dxf.c:12275 → 12276` | low | ✅ 通过 |

**正确的那一对是 `12284 → 12267`**（释放行在使用行的循环回边上）。
agent **既找到了 12284 这个释放点、也找到了 12267 这个使用点**，
但它把 **12284 配给了 12287**（另一处 `dxf_free_pair`）、把 **12267 配给了 12275**。

**→ 不是"没看见"，是"配对错了"。** 这两个是不同的失败模式，修法也不同。

### 我的判断（供你决定）

**按你定的判据"圈不到，这条路就有问题" —— 有问题。** 但问题是**具体的**，不是笼统的：

| 观察 | 含义 |
|---|---|
| **12284 和 12267 都被圈到了** | 它**看得见**这两行 |
| **却配成了 `12284→12287` / `12275→12267`** | 它**配对**是"释放行 ↔ 邻近的下一句"，不是"释放 ↔ 回边上的使用" |
| **224 处候选、重合率 20%** | 数量太多，而且两实例重合度低 → 置信度分层**几乎没起作用**（179 个 medium） |

**两个可能的方向**（都不做，等你说）：

| 方向 | 内容 |
|---|---|
| **(a) 改配对** | 让 agent **分开报**"释放点"和"使用点"两个列表，**配对交给程序**（同一个变量的自由与使用做笛卡尔积，再用控制流过滤）。这正好是"只报事实、不下判断"的彻底版 —— 配对本身就是一种判断 |
| **(b) 收窄输入** | 每批 6 个函数 → **1 个函数**，牺牲成本换注意力。R4 的教训是"20 次工具调用全花在第一个函数上"，反过来一次只看一个函数可能更专注 |

**224 处这个数本身也有问题** —— 你说过"圈出四百个的话，权重摊薄到没法用"。**224 已经很接近了。**
