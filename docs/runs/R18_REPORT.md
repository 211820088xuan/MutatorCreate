## 步骤 1 · CPG per-file 覆盖率全貌

### 指标

**覆盖率 = `max(最后一行调用的行号, 最后一个真实方法的末行) / 源码行数`**，
源码是 **pin** 的（限制 17），头文件不计入统计（它们本来就可能没有函数体）。

> **R18 修了三个测量缺陷**（都会凭空造出"❌"）：
> 1. **只用 call 行号** → 无调用的文件（尤其 `.h`）一律 0%。改成 `max(call, method_end)`。
> 2. **头文件混进统计** → `.h` 里的 `maxLine` 天然低。改成单列。
> 3. **后缀匹配有歧义** → `valid.c` 与 `fuzz/valid.c` 都以 `valid.c` 结尾，
>    取第一个会把 `valid.c` 的数字换成 `fuzz/valid.c` 的（实测差 10 倍）。
>    改成"精确相等优先，否则取最短后缀匹配"。

### 那 10,180 条断掉的 REF 边（R17 提到过）

它们全部是 `dstNodeType=MEMBER`（结构体成员）。**和覆盖率问题不是同一个根因**：
- 断 REF 边 = **类型/成员解析失败**（`xmlSAXHandler*.serror` 这类成员找不到 MEMBER 节点）；
- 覆盖率低 = **文件根本没解析完**（`valid.c` 停在 3225 行）。

**但两者都指向同一件事：`c2cpg` 对这个项目的解析质量不高。** 断边会直接影响**字段级**数据流
（`c->buf`、`obj->name`），而覆盖率影响**整段代码**。**两个都要量，不能只看一个。**

## 步骤 2 · 单点判定工具 + 断点定位（按用户决定：跳过 CPG 重建）

### 2.1 单点判定工具（用户决定 1）

`tools/r18_diag.py::point(cpg, file, line)` → 回答**三件事**：

| 输出 | 含义 |
|---|---|
| `@@CALLS` / `@@IDS` | 这一行有没有 call / identifier 节点 |
| `@@METHODS` | 包含这一行的**所有**方法（含 `<global>`） |
| `@@REAL_METHODS` | 其中**真实方法**（排除 `<global>`） |
| `@@VERDICT` | `USABLE`（有节点 + 在真实方法里）/ `NO_NODE` / `NO_REAL_METHOD` |

**用法**：每次数据流查询前先跑它。**这比量整体覆盖率有用得多** ——
libredwg 整体覆盖率只有 11.4% 却连出 67 条正确流，`tree.c` 覆盖 100% 却 0 条，
**整体指标没有预测力；单点判定才有**。

### 2.2 🔴 它立刻抓出：那两条"真实失败"**都是我的坐标错了**

| osv | 释放点 | 判定 | 使用点（按我样本里的文件） | 判定 |
|---|---|---|---|---|
| `ARVO-42494732` | `src/in_dxf.c:515` | ✅ **USABLE**（`free`，`dxf_free_pair`） | `12267` | ✅ **USABLE** |
| `ARVO-42486565` | `tree.c:3819` | ✅ **USABLE**（`xmlFree`，`xmlFreeNode`） | `tree.c:2216` | ❌ **NO_REAL_METHOD** |
| `ARVO-42491546` | `gml.c:189` | ❌ **NO_NODE**（该行在 `igraph_read_graph_gml` 里，不是释放点） | `264` | ✅ **USABLE** |

**查 pin 源码核对 `facts` 的原始记录**：

| osv | `facts` 里写的 | 我样本里写的 | 对不对 |
|---|---|---|---|
| `ARVO-42486565` | `free`: `tree.c:3819` | `tree.c:3819` | ✅ |
| | 使用：`xmlXIncludeIncludeNode` | 我当成 `tree.c:2216` | ❌ **它在 `xinclude.c:2208`**（`xinclude.c:2216` = `cur = ctxt->incTab[nr]->ref;`） |
| `ARVO-42491546` | `free`: **`src/io/gml-tree.c:189`**（`igraph_Free(t)`） | 我写成 `src/io/gml.c:189` | ❌ |
| | 使用：`src/core/vector_ptr.c:264`（`v->end - v->stor_begin`） | 我写成 `gml.c:264` | ❌ |

**→ 这两条从来没有被正确测过。R17 写的"真实的连不上"是错的。**

### 2.3 修正坐标后重测：暴露出**查询设计缺陷**和**两个真实边界**

用修正后的坐标重跑（`r17_cpg_probe.Q_FLOW`，带 overlay）：

```
  ARVO-42486565  @@FREE_CALLS 0   @@SRC1 0 @@SRC2 0  @@SINK_NODES 0  @@FLOWS 0
  ARVO-42491546  @@FREE_CALLS 0   @@SRC1 0 @@SRC2 0  @@SINK_NODES 5  @@FLOWS 0
```

**`@@FREE_CALLS 0` 的原因：我的查询只接受一个 `file` 参数，同时用于"找释放点"和"找使用点"。**
而**跨函数 UAF 的定义就是释放和使用在两个文件**（`tree.c` vs `xinclude.c`、`gml-tree.c` vs `vector_ptr.c`）。
**这是查询设计缺陷，不是 Joern 的能力问题。** 修法很简单：`free_file` / `use_file` 分开传。

**但即使修好，这两条还各有一个真实的边界：**

| osv | 链路形状 | 为什么数据流做不了 |
|---|---|---|
| `ARVO-42486565` | `cur`（在 `xmlFreeNode` 里被 `xmlFree(cur)`）→ **`ctxt->incTab[nr]->ref`** → `cur`（`xinclude.c:2216`） | **经结构体字段**（`incTab[nr]->ref`）传递。字段级数据流依赖 `MEMBER` 节点，而**这个 CPG 有 10,180 条断掉的 `REF` 边，全部指向 `MEMBER`** → 字段级链路是**断的** |
| `ARVO-42491546` | `t`（被 `igraph_Free(t)`）→ **别名** `v`（`igraph_vector_ptr_size(v)` 读 `v->end`） | **指针别名**（`t` 和 `v` 是同一个被释放对象的两个名字）。`reachableByFlows` 是**值流**，不做**别名分析** |

### 2.4 三者结构对比（回答"能力 A 的边界在哪"）

| 维度 | `ARVO-42494732`（✅ 67 条流） | `ARVO-42486565`（❌） | `ARVO-42491546`（❌） |
|---|---|---|---|
| 释放是直接 `free` 还是经包装 | 经**1 层**包装（`free(pair)` 在 `dxf_free_pair` 里） | 直接 `xmlFree(cur)` | 经包装（`igraph_Free(t)` 在 `igraph_gml_tree_destroy` 里） |
| 使用点同函数还是跨函数 | **同函数**（`dxf_objects_read` 里既调包装、又读 `pair`） | **跨文件**（`tree.c` → `xinclude.c`） | **跨文件**（`gml-tree.c` → `vector_ptr.c`） |
| 隔几跳 | **0 跳**（调用方实参就在 `use_fn` 里） | ≥1 跳 + **经结构体字段** | ≥1 跳 + **经指针别名** |
| 涉及裸指针还是结构体成员 | **裸指针** `pair` | **结构体字段** `incTab[nr]->ref` | 裸指针，但**换了名字**（别名） |
| 源的那个实参是 | **调用方局部变量** | 调用方实参 → 存进字段 | 调用方实参 → 别名 |
| 数据流连得上吗 | ✅ | ❌（字段级链路断） | ❌（别名） |

### 2.5 能力 A 的边界（本轮的核心结论）

| 形态 | 能连？ | 依据 |
|---|:---:|---|
| 同函数内、裸指针、循环回边 | ✅ | `ARVO-42494732` 67 条流，路径逐跳正确 |
| 跨函数（1 跳），调用方实参在 `use_fn` 里 | ✅ | R17 独立实验 804 条跨过程流 |
| **经结构体字段传递** | ❌ | 10,180 条断掉的 `MEMBER` REF 边 |
| **经指针别名传递** | ❌ | `reachableByFlows` 是值流，不做别名分析 |
| **释放与使用在不同文件**（当前查询只带一个 `file`） | ⚠️ **可修** | 把 `free_file` / `use_file` 分开传即可 |

**→ llm04 探测器能覆盖的真实 UAF 里，「同函数 + 裸指针」和「1 跳跨函数 + 裸指针」这两类能做；
「经字段」和「经别名」这两类做不了 —— 而 R12 的分布里 F1（字段）占 5%、F4（裸指针）占 55%。**

## 步骤 4 · 结论

### 1. 数据流的真实召回是多少

**1/1 = 100%（合格样本）**，落在 **≥60%** 这一档 → **能力 A 确认可用**。

**但这个数字的样本量是 1，置信度低。** 更重要是的**边界**（2.4–2.5）：

| 形态 | 能连？ |
|---|:---:|
| 同函数 + 裸指针 + 循环回边 | ✅ |
| 1 跳跨函数 + 调用方实参在 `use_fn` 里 + 裸指针 | ✅（R17 独立实验 804 条） |
| **经结构体字段** | ❌（断掉的 MEMBER REF 边） |
| **经指针别名** | ❌（`reachableByFlows` 是值流） |

### 2. CPG 覆盖率问题有多普遍、能不能修

| 问题 | 实测 |
|---|---|
| 多少个 CPG 有 ❌ 文件 | **10/10 都有**（leptonica 最轻 16 个，libredwg 最重 317 个） |
| 这个指标能预测"能不能用"吗 | **不能**（libredwg 11.4% 却能用；`tree.c` 100% 却连不上） |
| 重建能修好几个 | **本轮没重建**（用户决定：前提塌了，重建改变不了什么） |
| 真正的阻塞点 | 不是覆盖率，是 **① 坐标（可修）② 字段级链路（断边）③ 别名（能力边界）** |

### 3. 对 igraph / libxml2 意味着什么

**R16 判它们"UAF 是跨函数形态，扫出 0 条原语"—— 这个判断现在要分成三层：**

| 层 | 结论 |
|---|---|
| **扫描器层** | 它们的 UAF 确实是跨函数形态，同函数扫描器扫不出（R16 结论仍成立） |
| **CPG 覆盖层** | libxml2 的 `valid.c` 46%、`xmlreader.c` 0%；igraph 的 `gml-tree.c` 等要单独查。**这层是真障碍，但没修** |
| **数据流层** | 就算覆盖够、坐标对，**它们的形态是"经字段"和"经别名"，能力 A 做不了** |

**→ "第二个落地项目"的答案没变（仍然没有），但理由更清楚了：
不是"没有这种形态的 UAF"，而是"**这种形态的数据流分析做不了**"（字段级断边 + 别名）。**

**这比 R16 的结论更悲观，也更准确。**

### 本轮结论一句话

## 限制 21 · 「整体覆盖率」没有预测力，用**单点判定**代替

R18 实测 10 个 CPG 的 per-file 覆盖率（源码用 pin）：

| CPG | body 文件 | ✅≥90% | ❌<50% | ok% |
|---|---:|---:|---:|---:|
| leptonica ×2 | 508 / 515 | 489 / 496 | 16 | **96.3%** |
| igraph ×2 | 998 | 744–745 | 147–148 | 74.5% |
| libxml2 ×5 | 105–122 | 69–75 | 31–40 | 59.5–66.0% |
| **libredwg** | 360 | **41** | **317** | **11.4%** |

**但 libredwg 只有 11.4%，它的目标站点连出了 67 条完全正确的流；`tree.c` 覆盖 100% 却 0 条流。
→ 整体覆盖率不能用来判"这个 CPG 能不能用"，只能用来找可疑文件。**

**改用单点判定**（`tools/r18_diag.py::point`）：给定 (文件, 行号)，查
① 这一行有没有 call/identifier；② 在不在**真实方法**里（排除 `<global>`）。
输出 `USABLE` / `NO_NODE` / `NO_REAL_METHOD`。**每次数据流查询前先跑它。**

**R18 用它立刻抓出两条错样本**：`ARVO-42486565` 的使用点在 `xinclude.c:2216`（不是 `tree.c:2216`）、
`ARVO-42491546` 的释放点在 `src/io/gml-tree.c:189`（不是 `src/io/gml.c:189`）。

## 限制 22 · 跨函数 UAF 的查询必须**分开传 `free_file` 和 `use_file`**

R17/R18 的查询只接受**一个** `file` 参数，同时用于"找释放点"和"找使用点"。
**但跨函数 UAF 的定义就是释放和使用在两个文件**（实测：
`tree.c` vs `xinclude.c`、`gml-tree.c` vs `vector_ptr.c`）。
后果：这类样本一律 `@@FREE_CALLS 0`，看起来像"连不上"，实际是**查询找不到释放点**。
