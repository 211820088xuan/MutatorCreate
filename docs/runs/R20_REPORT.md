## 步骤 1b · 小实验：那 67 条流里有没有 (b) / (c) 形态（用户决定 3）

### 做法

把 R19 记录的 67 条完整路径（`docs/runs/r19/results.jsonl` 的 `paths`）逐跳拆开，
看**中间跳**里有没有 `->`（字段访问）。

### 结果：**67 条全是形态 (a)**

| | 条数 |
|---|---:|
| 中间跳**含** `->` | **57** |
| 中间跳**不含** `->` | 10 |
| **67 条里出现过的字段名（去重）** | **`code`、`value`** ← 都是 `pair` 自己的字段 |

样例（中间跳）：
```
  L12267:pair => L12267:pair != NULL => L12267:pair != NULL && pair->code == 0
  L12282:pair->code => L12289:pair->code => L12289:pair => L12289:pair->code => L12267:pair->code ...
```

**关键**：这些 `pair->code` 是**释放变量自己的字段**（形态 a），
**不是**"值经字段中转"（b），也**不是**"释放的就是字段"（c）。

**→ 按你的决策树：只有 a) → 要单独测 b)。**

### 顺带一个重要的技术细节

**数据流是能"穿过" `pair->code` 这个节点的** ✅ ——
但那靠的是**语法上的字段访问表达式**，**不需要 CALL→MEMBER 的 REF 边**。
所以"断边"和"能不能穿过字段访问"是**两件不同的事**。

### 目标名的形态

从加载日志里抓 `dstFullName`（libxml2 那张图，Top 6）：

| dstFullName | 条数 |
|---|---:|

**两种形态**：

## 步骤 3 · 根因：**是解析失败，不是设计行为**

### MEMBER 节点长什么样

```
  MEMBER 节点数    1,982
  name            content, compat_use, compat_size, alloc, contentIO, use, size, buffer, error, next, ...
  typeFullName    （取不到）
  fullName        （0 个节点有这个属性）
```

**MEMBER 节点只有 `name`（裸字段名），没有 `<类型>.<字段>` 形式的全名。**

### 断边要的键

`dstFullName = xmlParserCtxtPtr.input` —— **`<typedef名>.<字段>`**。

### 根因

**`c2cpg` 用 `<typedef名>.<字段>` 去查 MEMBER 节点，而 MEMBER 节点是按 `name` 存的（裸字段名），
且没有全名属性 → 查不到 → 边建不起来。**

两个具体成因：
1. **typedef 名 vs struct 名**：`xmlParserCtxtPtr` 是 typedef，底层是 `struct _xmlParserCtxt`；
2. **`ANY.xxx`**：类型没推出来（没做预处理器/宏展开，`libxml2` 的条件编译很多）。

**→ 这是 `c2cpg` 的类型解析能力问题，不是"设计上不建这种边"。**
证据：**MEMBER 节点是建了的**（1,982 个，名字都对），**只有引用链接失败**。
如果是设计行为，MEMBER 节点都不该建。

### 那 73 条成功的是什么

`成功率 = 73 / (73 + 10,180) = 0.71%`。**其余项目的成功率**：
libredwg 289/(289+113022)=0.26%、leptonica 71/(71+5872)=1.19%、igraph 2197/(2197+46327)=4.53%。

**成功的那些**应该是**类型能被静态确定**的（非 typedef、或同文件里直接定义的结构体）——
这需要进一步查，但**不影响主要结论**：**95%+ 的引用建不起来是能力问题**。

### 和覆盖率问题是不是同一根因

**不是同一个根因，但都指向 `c2cpg` 的解析能力**：

| 问题 | 表现 | 根因 |
|---|---|---|
| **断边** | MEMBER 节点建了（1,982），引用链接失败（99.29%） | **类型解析**（typedef / `ANY`） |
| **覆盖率**（R18） | `valid.c` 46%、`xinclude.c` 0%、`xmlreader.c` 0% | **文件级解析中途放弃** |

**两者独立**：断边率高的文件覆盖率可能很高（`tree.c` 99.97% 但字段引用全断）。

## 步骤 5 · 结论（回答开头四个问题）

### 1. 10,180 条占多大比例？

**99.29%**（断 10,180 /（断 10,180 + 成功 73））。
四个项目全部 **>95%**：libredwg 99.74%、libxml2 99.29%、leptonica 98.81%、igraph 95.47%。
**"其它型断边"四个图全是 0** —— 断边**全部**是 CALL→MEMBER 这一类。

### 2. 其他项目的图有没有同样的问题？

**有，而且 libredwg 最严重（113,022 条，99.74%）。** 这是 **`c2cpg` 的通病，不是 libxml2 特有。**

### 3. 根因是什么？

**类型解析失败，不是设计行为。**

| 证据 | 说明 |
|---|---|
| MEMBER 节点**建了**（1,982 个，名字都对） | 结构体定义解析成功 |
| 断边的目标键是 `<typedef名>.<字段>`（`xmlParserCtxtPtr.input`） | 而 MEMBER 只有裸 `name`、没有全名属性 |
| 大量 `ANY.<字段>`（858 条 `ANY.cur`） | 类型**根本没推出来** |

**→ `c2cpg` 用 `<typedef>.<field>` 去查按裸 `name` 存的 MEMBER 节点 → 查不到 → 边建不起来。
两个成因：① typedef 名 vs struct 名；② 没做预处理器/宏展开导致 `ANY`。**

**和 R18 的覆盖率问题不是同一根因**（都指向 `c2cpg` 的解析能力，但一个在文件级、一个在类型级）。

### 4. 能不能修？修好之后"经字段"那 25% 能不能做？

**不能修**（在"只读 pipeline、不改 c2cpg"的前提下）：
- typedef 名 vs struct 名是 **`c2cpg` 的类型系统**问题，脚本层改不了；
- `ANY` 是**没做预处理器**导致的，要改建图前端。

**而且即使修好，也解决不了"经字段"那 25%** —— 因为：

| 障碍 | 是断边造成的吗？ | 证据 |
|---|:---:|---|
| 形态 (a)：`free(pair)` → `pair->code` | ❌ | **67 条流已经穿过 `pair->code`** ✅ |
| 形态 (b)：值经字段中转 | ❌ | 卡在 **`xinclude.c` 覆盖率 0%**，不是断边 |
| 形态 (c)：`free(obj->buf)` → 读 `obj->buf` | 未测 | — |

**所以「断边 → 字段级数据流不可用 → 经字段的 UAF 做不了」这条因果链，三步证据都不支持。**

## 汇总

### 本轮结论一句话

**那 10,180 条断边是 `c2cpg` 的**类型解析失败**（用 `<typedef名>.<字段>` 去查只按裸 `name` 存的
MEMBER 节点），四个项目全部 >95%，不是 libxml2 特有、也不是设计行为；
但它**不是**"经字段 UAF 做不了"的原因 —— 数据流能穿过 `pair->code`（67 条流已证明），
形态 (b) 那条样本卡在 `xinclude.c` 覆盖率 0%，跟断边无关。**

| # | 问题 | 答案 |
|---|---|---|
| 1 | 10,180 条占多大比例 | **99.29%**（四个项目 95.47%–99.74%） |
| 2 | 其他项目有没有 | **有，libredwg 最严重（113,022，99.74%）→ `c2cpg` 通病** |
| 3 | 根因 | **类型解析失败**：`<typedef>.<field>` vs 裸 `name`；加 `ANY`（没做预处理器） |
| 4 | 能不能修 / 修好能不能做经字段 | **不能修**（要改 c2cpg）；**而且修好也解决不了经字段** |
