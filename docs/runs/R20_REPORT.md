# R20 报告

日期：2026-11-07
问题：**那 10,180 条断边到底是不是建图质量问题？**

> 背景（不重复论证）：R17 加载 `libxml2_d4d1f3f33d6d.cpg` 时 Joern 打出
> `Could not create edge ... edgeType=REF, srcNodeType=CALL, dstNodeType=MEMBER` 共 10,180 条。
> R18/R19 把它写成了"字段级数据流做不了"的原因（限制 25），**但从来没量过分母**。

---

## 步骤 1 · 规模（先有分母）

### 做法

断边**不在图里**（创建失败），所以只能从 **Joern 加载时打印的日志**数。
为了让每次真的重新加载，先 `rm -rf workspace/<cpg>/` 这个工作副本。

**注意**：`stderr` 合并进 `stdout` 会让行首错位 —— 解析必须用 `in` 而不是 `startswith`
（第一版因此全部解析成 `None`，`libxml2` 那轮我手工重跑才发现）。

### 四个 CPG 的结果

| CPG | MEMBER 节点 | 成功 CALL→MEMBER | **断掉** | **断占比** | 其它型断边 |
|---|---:|---:|---:|---:|---:|
| `libxml2_d4d1f3f33d6d` | 1,982 | 73 | **10,180** | **99.29%** | 0 |
| `libredwg_ff69eeda6658` | 7,349 | 289 | **113,022** | **99.74%** | 0 |
| `leptonica_90ec70fd4322` | 1,033 | 71 | **5,872** | **98.81%** | 0 |
| `igraph_c83b6ecdc3fe` | 2,709 | 2,197 | **46,327** | **95.47%** | 0 |

**断占比 = 断 /（断 + 成功）**，"其它型断边"（非 MEMBER）**四个图全是 0** ——
说明断边的**全部**是 CALL→MEMBER 这一类。

### 判定：落在哪一档

| 阈值（用户给的） | 实测 |
|---|---|
| **>50% → 字段级分析基本不可用，是真问题** | **✅ 四个图全部命中（95.47%–99.74%）** |
| 10–50% → 部分可用 | |
| <10% → 可能特例 | |

### 三个必须立刻指出的观察

**① 这不是 libxml2 特有，是**所有**项目都这样。**

libredwg 反过来最严重（**113,022 条，99.74%**）。**所以不是"某个项目的头文件没找全"，
是 `c2cpg` 的**普遍行为**。**

**② `MEMBER` 节点是**存在的**（1,033–7,349 个）。**

说明**结构体定义被解析了**，断的是**"字段引用 → 成员定义"的链接**（类型解析），
不是"结构体根本没解析"。

**③ 🔴 libredwg 的断边 99.74%，可它连出了 67 条正确的流。**

这条**直接动摇了限制 25 的因果**：R19 写"经字段的 25% 做不了，因为 10,180 条断边"。
但 **libredwg 的断边率更高（99.74% vs 99.29%），数据流照样连得上** ——
因为它连的是**变量的值流**，**不依赖 CALL→MEMBER 的 REF 边**。

**→ "断边 → 字段级数据流不可用 → 经字段的 UAF 做不了"这个链条，
至少有一环没有证据。** 步骤 2/3 要查的正是这一环。

### 关于文件的另一个细节

`workspace/` 下的工作副本：每测一个 CPG 就删一次再重建（约 20–235 s）。
`cpg_files/` 里的原图**一个都没动**（只读 ✓）。

### ⏸ 停止点：等确认

| 你要的 | 结果 |
|---|---|
| 四个 CPG 的断边占比表 | ✅ 见上（95.47%–99.74%） |
| 判定落在哪一档 | ✅ **>50% 那一档**（"字段级分析基本不可用，是真问题"） |
| 断边占**总 REF 边**的比例 | ⚠️ **没量**（flatgraph 没有 `graph.edges`，R17 踩过）。我量的是**更有意义的那个**：断边占"所有 CALL→MEMBER 引用"的比例 |
| MEMBER 节点数 | ✅ 1,033–7,349（**说明结构体定义解析到了**） |

**三个要确认的**：

1. **"总 REF 边"这个分母要不要补？** 我判断"CALL→MEMBER 的成功+断"这个分母更有意义
   （它直接回答"字段引用断了多少"），但如果你要"占全部 REF 边的比例"，我得换 API 再量一次。
2. **限制 25 的因果已经出现裂痕**（libredwg 99.74% 断边却连得上）。
   步骤 2 我按原计划查"断边集中在什么模式"，**但重点会放在"断边到底影响了什么"** ——
   因为这比"断边长什么样"更能决定限制 25 要不要改。
3. **往下的三步（2/3/4）可能都指向"断边不是经字段失败的原因"**。
   **要不要我先做一个小实验**：用 libredwg 那条**已经连上的**流，看它**有没有经过字段引用**？
   如果它经过字段也能连上，那"断边 → 字段不可用"当场就被推翻，可以省掉后面三步。
