## 步骤 1 · 把「扫描范围」和「读源码范围」分开

### 改法

`wrapper_frees_param()`（守卫 1）原来只在 **worklist** 里找被调函数，找不到就拒绝（R15）。
新增 `resolve_callee()`，按三级解析：

| 级别 | 来源 | 说明 |
|---|---|---|
| 1 | `worklist` | 原行为 |
| 2 | **CPG 的全部方法**（`build_all_funcs`） | worklist 的 10–30 倍（162 vs 5,129） |
| 3 | **pin 源码树**里按函数名搜（`_text_find`） | 最后兜底 |

**扫描范围仍然只有 worklist** —— 只扩"能读到的源码"。
配套：独立的 `SRC_CACHE2`（不污染 `scan_sites` 的 `src_cache`）+ 按原因计数 `_WRAP_REJECT_R`。

### 这本身就是一个结论

**解开的那 7 个函数，进入函数体后都正确地返回了 `False`**（它们确实只释放成员，不释放变量本身）。
**→ R15 的保守策略没有误杀真站点。** 它"运气好对了"。

### 顺带发现一个**范畴错误**（比步骤 1 本身更重要）

修好解析后我发现：`free(x)` / `LEPT_FREE(x)` / `xmlFree(x)` 这些**本身就是释放**，
但它们也被当成"包装函数"塞进了守卫 1 —— **查不到源码 → 拒绝 → 所有直接释放的站点被丢掉**。

窄条件修法：**只有当被调函数不在项目里、且名字像 free 原语时**才跳过守卫 1
（项目里的 `dwg_free_header_vars` 照旧走守卫 1，不会被跳过）。

**效果**：libredwg 原语 2→3、**leptonica 原语 0→1**（解锁！）。**新增的两条见步骤 2 的核实。**

## 步骤 2 · 同函数内的字段形态

### 实现要点

| 要点 | 做法 |
|---|---|
| 释放目标 | `FREE_CALL` 原来只支持**一层** `->`，改成**多层**（`a->b->c`、`a.b.c`） |
| 使用点匹配 | 同一个**字面字段路径**后续跟 `->`/`.`/`[` |
| 守卫照常 | 重赋值、置空、`return/break/continue/goto`、`#if 0` |
| **新守卫 1** | **宿主变量被重新赋值**（`free(obj->buf); obj = other; obj->buf[i]`）→ 挡 |
| **新守卫 2** | **`exit`/`abort`/`longjmp`/`_Exit`** → 挡（原来只查 `return/break/continue/goto`） |
| 站点标记 | 字段形态用 **`same_func_field`**（不混进 `same_path`/`loop_back`） |
