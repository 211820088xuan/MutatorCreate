# 变异算子生成：这一轮改了什么

> 面向需要向别人解释的读者。不假设你熟悉这套代码。
> 结论先说：**多策略算子已经造出来并跑完 A/B —— 复现达成，挖同类没达成。**

---

## 一、先讲清楚"变异算子"是什么

fuzzer 的本职是"乱改输入，看程序崩不崩"。

默认的乱改完全不懂格式 —— 它把 DXF 文件当成一堆随机字节，改了以后 99% 的情况解析器第一行就
拒了，等于白跑。

**变异算子（custom mutator）** 就是插进去的一段 C 代码，它知道一点格式：

```
默认变异器：随便挑几个字节翻一翻
变异算子  ：在 DXF 里找到 `2/OBJECTS` 这一段，把段里某条记录的名字改成随机串
```

这样改出来的输入**还能被解析**，只是内容变成了程序没预料到的东西 —— 才有机会触发 bug。

**单策略**：算子只懂一种改法（比如只改 OBJECTS 段）。
**多策略**：算子懂好几种改法，按比例分流（比如一半预算走默认、四分之一改 OBJECTS、四分之一改 ENTITIES）。

## 二、改动之前的状态：有一个好算子，但造不出第二个

已有的东西：

| 项 | 值 |
|---|---|
| 单策略算子 | `mutator.c`，sha1 `d7913b9e` |
| 它的战绩 | 同一个种子、同样的时间，**默认变异器 0 次崩溃，它 617 次** |

这个 617 vs 0 是整条线的地基 —— 证明"懂格式的算子确实有用"。

**问题**：想再造一个"懂 ENTITIES 段"的算子，造了四轮，四次都失败，而且**每次失败的方式都不一样**：

| 轮次 | 现象 |
|---|---|
| R28 | 4 个策略一起生成，被门禁拒 |
| R29 / R30 | 2–3 个策略能过门禁，但产出的是**同一个算法换了个随机种子**（换 salt） |
| R31 | 3 个策略，生成的代码是 **no-op**（什么都不做） |
| R34 | 3 个策略，代码去改组码行（把 DXF 的结构骨架改了） |

四次都是"看到现象就换个方案"，**一次都没打开被拒的那份代码看过**。

## 三、根因：一处字段路径错配，三条读路径全落空

### 3.1 查到的东西

真正把这件事解开，是 R35 做的一件事：**把文件名里带 "entities" 的那份算子打开读**。

结果：

```
"ENTITIES" 出现次数：0
它找的是：  S_OBJECTS[] = {'O','B','J','E','C','T','S'}
它插的是：  0\r\nSECTION\r\n2\r\nOBJECTS\r\n0\r\n
函数名：    construct_objects_section
```

**那不是 ENTITIES 算子，是"文件名叫 entities 的 OBJECTS 算子"。**

R28–R34 四轮"多策略造不出来"的结论，**全部建立在这个假前提上**。

### 3.2 为什么会这样

管道的设计本身是对的：`find_call_site()` 从源码里的守卫

```c
strEQc (pair->value.s, "OBJECTS")
```

把段名抓出来，写进 `mutations[].locator.section_anchor`。

**问题在读的那一侧**：

| 读的地方 | 读的路径 | 结果 |
|---|---|---|
| `plan_anchor()` | `targets[].section_anchor` | ❌ 空 |
| `plan_anchor()` | `mutations[].site.var`，要求全大写 | ❌ libredwg 里是 `pair`，小写 |
| `_sample_hex` 调用处 | `tgt.get("section_anchor")` | ❌ 空 |

三条全落空 → 四处 `or "OBJECTS"` 兜底 → **恰好 libredwg 的真值就是 OBJECTS，所以这个 bug 从来没显形**。

换成 ENTITIES 站点时：`find_call_site` 抓到 `"ENTITIES"` 写进 locator，但**没人读得到** →
回退 OBJECTS → 喂给 LLM 的字节样本采的是 **OBJECTS 段** → 它从头到尾只看得见 OBJECTS →
产出 OBJECTS 代码。

**不是 LLM 写不出 ENTITIES，是它从来没被要求写 ENTITIES。**

这类"错得不响"的问题，这个项目里记到第九个，给它的名字叫**静默失败**：
回退值恰好等于正确值，所以测试、门禁、人眼全都看不出来。

### 3.3 怎么修的

读路径改成三级，按可信度排：

```python
def plan_anchor(plan):
    for m in plan.get("mutations") or []:          # ① locator —— 真正的写入位置
        a = (m.get("locator") or {}).get("section_anchor")
        if a: return a
    for t in plan.get("targets") or []:            # ② targets —— 历史路径，保留
        if t.get("section_anchor"): return t["section_anchor"]
    ...
```

并且把四处 `or "OBJECTS"` **改成硬失败**：拿不到锚点就 `die()`，不许静默回退。

> **为什么硬失败很重要**：静默回退让一个错误看起来像成功。宁可让流程停下来，
> 也不要它悄悄用了错的值。

### 3.4 修完的验证

| 检查 | 结果 |
|---|---|
| 现有 libredwg plan | `plan_anchor()` = `'OBJECTS'` ✅（真值就是它，行为不变） |
| ENTITIES 假 plan | `plan_anchor()` = `'ENTITIES'` ✅ |
| 空 anchor | `None` → `die()` ✅ |
| `construct.sequence`（构造路径那一段）是否跟着换 | ✅ **跟着换**（用替换 `find_call_site` 的方式实测，不是看代码推断） |
| 单策略 ENTITIES 生成 | ✅ 代码里 `ENTITIES` 出现 2 次，**门禁全过**，sha1 `63b23547` |
| 1000 seed 能力剖面 | ✅ CHANGED **500/1000**、DISTINCT 496、**改动 100% 落在 ENTITIES 段** |

**这是 ENTITIES 算子第一次真的产出 ENTITIES。**

## 四、另外三处改动（都是为了让"多策略"能成立）

### 4.1 去掉"结构合法性"门禁

**原来**：生成完要检查"输出里有没有 `0/SECTION + 2/<锚点> + 一条 code-0 记录`"。

**问题**：这是用"**长得像不像 DXF 的段**"去**猜**"这个变异有没有用"。
`ACAD_` 那种形态（`handle.value == 0xC` + 版本 ≥R2007）**根本不是"段 + 记录"**，永远过不了。

**改法**：去掉这一道，其余四道保留。

> 保留的四道验的是"**算子有没有在干活**"：default 权重对不对、1000 seed 产出多少个不同输出、
> 该保持不变的地方有没有被改、剥掉目标段的种子上有没有产生改动。
> R31 那次生成出 no-op，就是前两道抓出来的。

**去掉之后的实际结果**：3 个策略的生成又被 `preserve=group_code_digits` 挡住（45/50 采样改组码行）。
**这一次判断是"门禁挡得对"** —— 组码是 DXF 的结构骨架，改了就不是合法 DXF。
所以这一道**保留**，失败的责任在 LLM 写不出合格代码。

### 4.2 `generation_gate` 不再写死 `pending`

`mutator.json` 里有个 `generation_gate` 字段，以前是**写死的静态字典**，
永远是 `pending`，从来没人更新。

**改法**：`verify` 跑完之后把真实结果**回写**进去，并标上 `_filled_by: verify`。

### 4.3 V4 第一次真正跑起来

`verify` 有四道门禁，其中 **V4（行为门禁）** 要拿一个已知会崩的输入去回放，
确认算子没把"能触发目标崩溃"这个能力弄丢。

**以前它一直是 `NOT_APPLICABLE`** —— 因为 `source_context.json` 里没有 `testcase_path`，
它根本不知道拿什么回放。

**改法**：从历史崩溃样本里挑一个，回放确认它确实崩在 `in_dxf.c:12267`，写进 `testcase_path`。

**结果**：

```
V4_behavior  PASS  · 已知 crash 回放: heap-use-after-free /src/libredwg/src/in_dxf.c:12267
```

**这是 V4 第一次真正验证了东西**，不再是"没跑但显示通过"。

## 五、多策略最终是怎么造出来的：并列拼接

### 5.1 为什么不"一次生成多个"

四次尝试、四种失败方式，说明**"让 LLM 一次写出多个能跑的独立策略"这个动作本身太难**。

所以换思路：**一次只生成一个**（这个一直成功），然后**用程序把它们拼起来**。

### 5.2 拼接：模式 B

有两种合并方式：

| 模式 | 做法 | 问题 |
|---|---|---|
| A 参数化合并 | 提公共骨架，差异提成参数 | 需要理解算子内部逻辑；只在"两个算子几乎一样"时可行 |
| **B 并列拼接** | 各自保留完整函数体，只在入口分流，符号加前缀 | **任何情况都能用** |

**选 B。** 理由是它**不需要理解算子内部** —— 符号重命名是纯机械操作，可以做到 100% 准确。

### 5.3 符号重命名：用 `nm`，不用正则

这是个关键细节。

**错的做法**：写正则去匹配 `static` 声明。C 的声明形态太多（`static`、`static inline`、
函数指针、数组、宏展开……），正则必错。

**对的做法**：编译成 `.o`，让链接器告诉你哪些是局部符号：

```bash
gcc -c -O0 x.c -o x.o
nm x.o | awk '$2 ~ /^[tdbrs]$/ { print $3 }'
```

- 小写 `t/d/b/r/s` = 局部符号 → 要加前缀
- 大写 `T/D/B` 和 `U`（外部引用）→ **一个都不许改**

改名只在标识符边界上做（`\bfoo\b`），**且不动字符串字面量内部** ——
先把字面量挖成占位符，改完再放回。

### 5.4 拼出来的样子

```c
size_t LLVMFuzzerCustomMutator(uint8_t *Data, size_t Size, size_t MaxSize,
                               unsigned int Seed)
{
  unsigned int r = Seed % 1000u;
  if (r < 500u) return LLVMFuzzerMutate(Data, Size, MaxSize);   /* default 0.50 */
  if (r < 750u) return s001_entry(Data, Size, MaxSize, Seed);   /* 0.25  OBJECTS */
  return s002_entry(Data, Size, MaxSize, Seed);                 /* 0.25  ENTITIES */
}
```

**分流只用 `Seed`，不读 `Data`** —— 这样"同一个 seed 在两个算子里应该产出同样的字节"才能验证。

## 六、验收：三条硬指标

拼接是机械操作，但**机械操作也可能改坏逻辑**，所以必须验。

| # | 判据 | 结果 |
|---|---|---|
| 1 | **等价性**：多策略的 s001 分支产物，和原单策略算子逐字节比 | **250/250** |
| 1 | 同上，s002 vs 原 ENTITIES 算子 | **250/250** |
| 2 | **权重**：1000 个 seed 怎么分流 | **default 500 / s001 250 / s002 250** |
| 3 | **落点不重叠**：两个策略改的字节区间是否互不重叠 | **OBJECTS 段 250 / ENTITIES 段 250 / 其它 0** |

第 1 条是关键：它证明**重命名没改坏任何逻辑**。

> 中间有个插曲：第一次测得 249/250，我以为是重命名的问题。查下来是**测试区间取错了** ——
> seed 750 在拼接版里分流到 s002，不属于 s001 分支。改成 500–749 后 250/250。

门禁 V1–V4 也全过（V4 真跑）。

## 七、A/B：两组，各答一个问题

**A 臂** = 不挂自定义算子的默认 fuzzer；**B 臂** = 挂多策略算子的 fuzzer。
除算子外所有条件一致。

### 为什么要跑两组

| | 种子 | 答什么 |
|---|---|---|
| **组 1 可比性** | 单个 `Constraints.dxf` | 多策略 **vs 单策略**（和 617 vs 0 同一个口径） |
| **组 2 真实性** | 整个 `seeds/` 文件夹 | 换 8 个种子，还成不成立 |

组 1 用单种子是为了可比性（`reps_r9_final` 就是这么跑的）。
**但单种子有过拟合风险** —— 那个文件的 OBJECTS 段正是算子生成时采样用的样本，
算子可能只"记住"了这一个文件。组 2 就是来测这件事的。

### 结果

| 组 | A（默认） | B（多策略） | **B/A** |
|---|---|---|---|
| 组 1（300s × 5 reps，per-exec 率中位） | 91.00 / 百万次 | **1524.15 / 百万次** | **16.7×** |
| 组 2（`-runs=120000` × 3 reps，崩溃文件数） | 330 | **784** | **2.4×** |

**两组方向一致（都是 B 更好），幅度差别很大（16.7× vs 2.4×）。**

这个差别**正是设计两组的目的**：组 1 的 16.7× 里，有一部分是"记住了那一个文件"带来的。
换成 8 个种子后摊薄到 2.4×。**所以不算严重过拟合，但组 1 的数字不能单独引用。**

### 🔴 但"挖同类"没达成

"挖同类"的意思是：**能不能撞出 12267 之外的新崩溃点**。

答案：**没有**。

```
两组、两臂、11 个独立 run，所有崩溃全部落在 in_dxf.c:12267 一个点。
抽样回放：A 臂 30/30、B 臂 47/47 全是 heap-use-after-free in_dxf.c:12267
```

**"复现"达成了**（585 次 vs 617 次，同一量级）；**"挖同类"没达成**。

## 八、试过但没做成的一件事（如实记录）

本来还想给门禁加一个**"执行门禁"**：不再用"输出长得像不像段"去猜，
而是直接在源码里插桩，测"这次变异有没有让执行走到目标那一行"。

**卡住了，最后停止开发。** 值得记下来的是**卡住的方式**：

调试了四轮，最后一轮报告"60 个插桩点全部插入成功、编译通过"，
但自检时**一个插桩标记都没打出来**。查下去发现：

```bash
源文件里 R36_ 出现次数      → 0
二进制里 R36_ 出现次数      → 0
```

**两条都是 0** → 说明"插入"根本没落地。

真因是脚本里这一行：

```python
_sh(f"rm -rf {COV_SRC} && cp -a /src/libredwg {COV_SRC} && ...")
```

`rm -rf` 执行了（副本没了），`cp -a`（1.3 GB）**没落地**，而 `_sh` **不检查返回码**，
代码照样往下走。后面所有写入都落进一个不存在的目录。

**而"60 个插桩点"是 Python 侧 `len(slots)` 数出来的，不是编译器的确认。**
这两个数前四轮一直被当成同一件事 —— 这就是为什么一直没查到这一层。

同时也要记一笔：**我在这件事上给出的三次诊断都是错的**
（"累积偏移"、"覆盖率报告坏了"、"tab 丢前缀"），
每次都是原始数字把我纠正过来的。**原始数字比诊断可靠。**

## 九、可以用一句话解释的版本

> 之前那个"懂 DXF 的变异算子"确实有用（默认 0 次崩溃，它 617 次），
> 但想再做一个"懂另一段"的，造了四轮都失败。
> 查下来不是模型不会写，是**管道里有一处读错了字段名**，
> 导致不管要什么段，喂给模型看的永远是 OBJECTS 段 —— 而回退值恰好等于正确值，所以一直没暴露。
> 修好之后，第二个算子几分钟就出来了。
> 然后把两个算子用程序（不是模型）机械拼成一个多策略算子，逐字节验证拼接没改坏逻辑，
> 再跑 A/B：单种子下多策略是默认变异器的 **16.7 倍**，换成 8 个种子是 **2.4 倍**。
> **唯一没做到的是"撞出新的崩溃点"—— 11 个独立 run 全部落在同一个位置。**

## 十、这次改动留下的三条教训

1. **回退值恰好等于正确值，是最难发现的 bug。**
   四处 `or "OBJECTS"` 让一个错误看起来像成功。修法是**硬失败**，不是改对回退值。

2. **"我数出来的数"和"编译器确认的数"不是一回事。**
   插桩那次四轮都栽在这上面。以后凡是"插了 N 个点"，必须用 `strings`/`grep` 在产物里核一遍。

3. **打开被拒的代码看，比换方案快得多。**
   前四轮每次都是"看到现象就换方案"，第五轮读了那份代码，十分钟就定位到了根因。
